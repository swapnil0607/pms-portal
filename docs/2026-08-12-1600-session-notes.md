# PMS Session Notes — 12-08-2026 04:00 PM

Summary of the changes made to the EduRiser PMS in this working session, for reference/handoff. Covers what changed, why, which files need to be re-uploaded via FileZilla, and whether any database/phpMyAdmin action is required.

---

## 1. Daily Log: "Client Name" → "Project Name"

**Why:** The Daily Log form's main field was labeled "Client Name" but projects matter more than clients for reporting. It also mixed client names and project names together in the autosuggest.

**What changed:**
- Label and placeholder changed from "Client Name" to "Project Name" on the homepage quick-add form, the `/work-logs` page, and the `/work-logs/edit` page.
- The autosuggest/cascade behind that field now sources strictly from real `projects.name` rows — no more client names or stray historical free-text mixed in.
- Archived projects are excluded from this suggestion list (see #6).

**Files:** `app/Models/Suggestions.php`, `app/Views/dashboard.php`, `app/Views/work_logs/index.php`, `app/Views/work_logs/edit.php`, `public/index.php`

**DB/SQL needed:** None.

## 2. Time Logs: month picker redesign

**Why:** Wanted a simpler month navigator instead of the Month/Date Range toggle.

**What changed:**
- Removed the "Date Range" mode entirely — Time Logs is month-only now.
- Replaced the plain month input with a `‹ Month ›` stepper: arrows step one month at a time and auto-apply; clicking the month text still opens the native month/year picker for jumping further.

**Files:** `public/index.php`, `app/Views/time_logs/index.php`, `public/assets/js/app.js`, `public/assets/css/app.css`

**DB/SQL needed:** None.

## 3. Time Logs: click a task in the breakdown to open it

**Why:** Wanted to jump straight from a Time Logs drill-down row to the actual task.

**What changed:** Leaf rows in the Time Logs breakdown (both "View by User" and "View by Client") are now links to `/tasks/show?id=...` whenever that log entry is tied to a real Task. Rows that are still plain free-text (no linked task) stay as plain text — nothing to jump to.

**Files:** `app/Models/WorkLog.php`, `public/index.php`, `app/Views/time_logs/index.php`, `public/assets/css/app.css`

**DB/SQL needed:** None (reads the existing `tasks.id` relationship).

## 4. Reports: search fields scoped correctly per tab

**Why:** The "Client Name" search box on the Reports page showed a mix of client names and project names on every tab, including the Project Report and Customer Report tabs where that's confusing.

**What changed:**
- **Project Report tab:** search field relabeled "Project Name", now suggests only real project names.
- **Customer Report tab:** search field stays "Client Name", now suggests only real client names (from the `clients` table).
- Detailed Work Log tab is unchanged (general search, as before).

**Files:** `app/Models/Suggestions.php`, `public/index.php`, `app/Views/partials/suggestions.php`, `app/Views/reports/index.php`, `public/assets/js/app.js`

**DB/SQL needed:** None.

**Known follow-up (not fixed, flagged only):** The Customer Report's *numbers* (not the search box) still group by the raw logged project text, which increasingly holds project names rather than client names — a client with several projects may start showing as separate rows there instead of one combined total. Not fixed yet; revisit if the report starts looking fragmented.

## 5. Homepage: "Find a Task" search bar

**Why:** Wanted a fast way to jump straight to any task from the homepage.

**What changed:** New panel under the stats cards on Home:
- Type-ahead search by task title (2+ characters), showing each match's Project › Phase › Task List path; click a result to open it.
- A "Filters" toggle with cascading Client → Project → Phase → Task List dropdowns; picking any of these filters results too, even with no text typed.

**Files:** `app/Models/Task.php`, `public/index.php`, `app/Views/dashboard.php`, `public/assets/js/app.js`, `public/assets/css/app.css`

**DB/SQL needed:** None. Adds one JSON endpoint, `/tasks/search`, used only by this search box.

## 6. Archived projects excluded from Daily Log suggestions

**Why:** An archived project (e.g. "Tabuk Pharma 2025-26 - LMS Only") was still showing up in the Daily Log's Project Name autosuggest.

**What changed:** The Daily Log's project/phase/module suggestion tree now excludes any project with `archived_at` set, at every point it could otherwise re-appear.

**Files:** `app/Models/Suggestions.php`

**DB/SQL needed:** None.

## 7. Removed "Task Category" from Daily Log

**Why:** The dropdown (SB/VD/DEV/QA/PUB/TRN/MNT codes) didn't mean anything to the team.

**What changed:**
- Dropdown removed from the homepage quick-add form, `/work-logs`, and `/work-logs/edit`.
- New entries silently save with a fixed placeholder category (`DEV`) behind the scenes, since the database column is still required internally for reports/exports.
- Editing an existing log preserves whatever category that log already had — editing for an unrelated reason (e.g. fixing hours) never silently recategorizes it.
- **Follow-up bug fix (same day):** the Edit Time Log save was still rejecting saves whenever a log's stored category wasn't one of the 7 old codes (true for most older/imported logs) — its error said "Please fill in Task Category, Activity, and a valid number of hours." even when Activity and Hours were correctly filled in. That check has been removed entirely from both Save (create) and Save Changes (edit); editing old logs works again regardless of their original category value.

**Files:** `app/Views/dashboard.php`, `app/Views/work_logs/index.php`, `app/Views/work_logs/edit.php`, `public/index.php`

**DB/SQL needed:** None.

## 8. New Daily Log entries auto-link to a real Task (clickable in Time Logs)

**Why:** Entries logged via the plain Daily Log form were never linked to a real Task record, so they could never be clicked through from Time Logs — unlike entries logged from a Task's own "Log Work" panel, which always were.

**What changed:** On every new Daily Log save, the app now automatically finds-or-creates a matching Task behind the scenes (using Project Name / Project Phase / Module Number & Name to place it, and the Activity notes as the task's title), and links the log to it:
- If a task with that exact title already exists in that Task List, it's reused (so repeated/recurring entries share one task instead of creating duplicates).
- The auto-created task is marked **completed / 100% progress** immediately, since a daily log always describes work already done — it won't show up as an open item in Kanban or "My Work".
- If the typed Project Name doesn't match a real, non-archived project, the log still saves exactly as before — it just stays unlinked (never blocks saving).
- Editing an existing log does **not** re-run this logic — only new saves get an automatic link, so editing an old log never risks creating an unexpected duplicate task or changing its link.

**Files:** `app/Models/Task.php`, `public/index.php`

**DB/SQL needed:** None directly — but this does create new rows in `project_phases`, `task_lists`, and `tasks` over time as people log work (expected, not a bug).

## 9. One-time backfill for previously-unlinked entries

**Why:** A handful of entries logged before item #8 shipped (the ones showing "DEV" in Time Logs, non-clickable) needed the same fix applied retroactively, without touching anything else.

**What was built:** [`migration/backfill_task_links.php`](../migration/backfill_task_links.php) — a standalone, token-gated, web-runnable one-time script using the exact same find-or-create logic as #8.

**How to run it (if not already done):**
1. Upload just this one file via FileZilla into a `migration` folder on the server (create the folder if it doesn't exist there — none of the other files in the local `migration/` folder are needed).
2. Visit once in a browser:
   `https://eduriserck.com/pms/migration/backfill_task_links.php?token=a3eccf450b41536257055e43cd42063f9494e9bafce86a25`
3. Read the plain-text report (`LINK`/`SKIP` per row, plus totals).
4. **Delete the file from the server afterward.**

**Safety, verified against a local copy of the production data before recommending this:**
- Only ever sets `work_logs.task_id` on rows where it was `NULL` — no other column on those rows is touched, nothing is ever deleted.
- Never guesses/creates a Project — a row whose typed project name doesn't match a real project is skipped and reported, left exactly as-is.
- Idempotent — safe to run more than once; already-linked rows are simply skipped on a re-run.

**DB/SQL needed:** None via phpMyAdmin — the script does the DB work itself when visited.

## 10. Discussed but not built: bulk-marking old tasks "completed"

Separately discussed: clearing out the "My Work" section by marking every currently open/in-progress/review/blocked task as `completed` as a one-time reset, going forward relying on the normal assign→close workflow. This was provided as a **SQL snippet for you to run yourself in phpMyAdmin** (not something I could run — no reachable connection to the live database from here), together with a recommended backup-first step. Confirm with your own notes whether this was actually run; it's independent of everything else in this document.

```sql
-- Preview first:
SELECT COUNT(*) FROM tasks WHERE status <> 'completed';

-- Then, if that count looks right:
UPDATE tasks
SET status = 'completed', progress = 100
WHERE status <> 'completed';
```

This only touches `tasks.status` / `tasks.progress` — never `work_logs` or any other table.
